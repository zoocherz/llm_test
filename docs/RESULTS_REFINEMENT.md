# Импорт, выборочные повторы и независимые оценки

Требования владельца, 2026-09-22. Владелец подтвердил: выборочные повторы отображаются в исходном запуске. Предыдущие попытки сохраняются, snapshot не меняется. Реализация начата; предложение отдельного Run ниже заменено этим решением.

## Подтверждённые причины

- apply_import_mapping уже оборачивает входной текст в input.text, но reference_field принудительно разбирает как JSON-объект. Обычный текст эталона поэтому отклоняется.
- RunResults.itemResultText проверяет truthy output_json.text и иначе пишет «Результат отсутствует» без учёта статуса. Это смешивает пустой ответ, ожидание и ошибку. Причина конкретного ответа OpenRouter пока не установлена; лимиты провайдера нельзя считать причиной без проверки.
- В Workbench история стоит перед текущими результатами; тип запуска отсутствует в колонках, хотя snapshot.kind уже различает generation/evaluation.

## Требования и критерии приёмки

1. При сопоставлении эталона предложить «Обычный текст» и «JSON-объект». Текст преобразуется в reference.text, JSON разбирается только при явном выборе. Показать исходное и преобразованное значения первых строк; ошибочный JSON не преобразовывать молча в текст. Существующие API-клиенты с JSON-сопоставлением сохранить совместимыми.
2. Выборочный повтор по RunItem (конкретная строка × модель × промпт), а не повтор всех комбинаций строки. Действия: выбранные, все с ошибкой, все без результата. Не повторять выполняющиеся элементы; показать точный объём вызовов перед запуском. Подтверждено владельцем: тот же Run и snapshot, новая Attempt, прежние ответы и оценки доступны в истории. Старые отдельные оценки сохраняют захваченные ответы. Отменённые и legacy Run пока не допускаются к повтору.
3. Различать ожидание, ошибку, пустой ответ и полученный ответ. Для текстовой генерации пустой/пробельный ответ не считать успешным полезным результатом. Исторические completed не переписывать; показывать предупреждение. Проверить adapter/runner и реальные метаданные проблемного Run без вывода raw data/secrets.
4. Текущие результаты выше истории; после явного запуска/выбора переход к результатам, без постоянного scroll при polling. История ограниченной высоты или с пагинацией.
5. Каждый критерий имеет собственные min/max, например 0..5; отдельные баллы и сводки по каждому критерию. Независимый режим не требует суммы весов 1 и не создаёт общий score/pass-fail. Прежний weighted-режим 0..1 сохраняется для старых suites/snapshots. Диапазоны входят в immutable snapshot и контракт ответа Judge; сервер проверяет конечные числа и границы. Экспорт сохраняет ключи, шкалы и значения, а не только среднее.
6. В истории и карточке явно показывать «Генерация ответов» / «Оценка судьёй», источник оценки и связь повторов. Для legacy не угадывать тип: «Старый запуск».

## Последовательность и проверка

Реализация проверена: 28 backend tests, production build и 10 browser E2E прошли. В рабочей базе read-only проверкой подтверждены пустые completed text outputs; конкретную причину на стороне OpenRouter по сохранённым данным установить нельзя. Старые записи не изменялись.

Сначала импорт/пустые ответы/навигация, затем выборочный повтор и независимые шкалы с API-контрактами. Backend tests: текст/JSON эталона, пустой ответ, точный subset и сохранность snapshot, границы оценок и совместимость. Browser tests: preview преобразования, видимость текущего результата, тип запуска, выбор записей, критерии 0..5 без весов. Реальные вызовы провайдеров без отдельной необходимости не выполнять.
