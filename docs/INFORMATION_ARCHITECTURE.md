# Информационная архитектура интерфейса

## Статус

Рабочая UX-спецификация после проверки быстрого запуска и разбора `docs/scenarios.md`. Черновик владельца используется как discovery-вход: подтверждённые требования переносятся в канонические документы, но сам файл не становится жёсткой спецификацией.

## Проблема текущего интерфейса

`EvaluationWorkbenchView` объединяет быстрый запуск, импорт Dataset, настройку ModelRoute, Prompt/Pipeline/EvaluationSuite, запуск, историю и детали результата. Это было полезно для проверки vertical slice, но плохо масштабируется и не соответствует ментальной модели пользователя.

Пункты `Providers`, `Tasks` и `Test Runs` относятся к старому домену `Provider/Task/TestCase/TestRun`. Они не управляют универсальными сущностями v1 и не должны выглядеть как равноценные разделы продукта.

## Основной пользовательский цикл

1. Подготовить или выбрать Dataset.
2. Настроить кандидата: модель, prompt, параметры и при необходимости pipeline.
3. Запустить получение ответов.
4. Выбрать или настроить evaluators, включая LLM Judge.
5. Выполнить оценку.
6. Сравнить варианты в сводной таблице и открыть отдельные примеры.
7. Повторить эксперимент с другой моделью, prompt или настройками.

Доменное соответствие не меняется:

`DatasetVersion → PipelineVersion + ModelRoute + PromptVersion → RunSnapshot → RunItem/Attempt → EvaluationResult`.

## Целевая верхнеуровневая навигация

| Раздел | Задача пользователя | Основные сущности |
| --- | --- | --- |
| Главная | Быстро начать сравнение и продолжить недавнюю работу | DatasetVersion, ModelRoute, Run |
| Датасеты | Импортировать, проверить, разметить, версионировать и просматривать данные/assets | Dataset, DatasetVersion, DatasetItem, Asset |
| Модели | Настроить подключения, выбрать модели из каталога, проверить доступность и capabilities | ModelRoute и provider catalog |
| Эксперименты | Определить, что сравниваем: dataset, prompt, модели, параметры, pipeline и набор оценки | PipelineVersion, PromptVersion, EvaluationSuiteVersion |
| Запуски | Следить за выполнением, сравнивать результаты, изучать примеры и экспортировать snapshot | RunSnapshot, RunItem, Attempt, EvaluationResult |
| Оценка | Управлять переиспользуемыми критериями, метриками и Judge-конфигурациями | Evaluator, EvaluationSuiteVersion, Judge route/prompt |
| Настройки | Диагностика, журналы, defaults, retention и локальные системные параметры | системная конфигурация |

На первом шаге реализации постоянными пунктами достаточно сделать `Главная`, `Датасеты`, `Модели`, `Эксперименты`, `Запуски`. `Оценка` выделяется из Эксперимента, когда появится библиотека evaluator-конфигураций. `Настройки` появляется только с реальными пользовательскими действиями; пустые разделы не создаются.

## Progressive disclosure

### Главная

- Быстрый запуск: тексты, сохранённые модели, оценка числа вызовов, запуск.
- Недавние запуски и явный переход к результатам.
- Ссылки «Добавить модель» и «Создать датасет», если prerequisites отсутствуют.
- Никаких JSON, UUID и терминов `ModelRoute`/`Version` в основном пути.

### Датасеты

- Список датасетов и их опубликованных/черновых версий.
- Создание через вставку текста, CSV/JSONL и в дальнейшем загрузку файлов/assets.
- Preview и validation до записи, затем явные commit/publish.
- Опубликованные версии immutable. Действие «Новая версия» использует ту же preview/import форму, создаёт пустой draft только при сохранении и публикует полный replacement-набор; предыдущая версия остаётся доступной.
- Разметка с помощью LLM, произвольное преобразование схем и генерация синтетических данных — отдельные будущие workflows, а не скрытые опции базового импорта.

### Модели

- Сохранённые подключения и состояние credential без показа secret.
- Каталог моделей, поиск, free-first фильтр, modalities/capabilities и известные лимиты.
- Создание, изменение, удаление и диагностический smoke.
- Одна сохранённая модель может использоваться кандидатом, генератором эталонов или Judge; роль задаётся в Experiment/EvaluationSuite, а не дублирует ModelRoute.

### Эксперименты

- «Что тестируем» — версионированная конфигурация, а не новая конкурирующая доменная сущность.
- Базовый режим: один DatasetVersion, один PromptVersion, несколько ModelRoute и EvaluationSuiteVersion.
- Расширенный режим раскрывает параметры модели, bindings, линейный PipelineVersion, timeout/concurrency/budget.
- До старта показывается матрица вариантов и количество candidate/Judge calls.

### Запуски

- Отдельные состояния queued/running/terminal, progress и cancel.
- Сводная матрица по моделям: success/error rate, latency, usage/cost и quality.
- Drill-down в DatasetItem: вход, reference, outputs, attempts, evaluator/Judge results и safe normalized errors.
- JSON/CSV export и immutable snapshot.

## Судьба legacy-разделов

- `Providers`, `Tasks`, `Test Runs` убрать из основной навигации: новые функции на них не строятся.
- Их компоненты и API не удалять одновременно с первой перестройкой UI. На переходный период они могут быть доступны только по `/legacy/...` для диагностики старых записей.
- Новый раздел `Модели` использует v1 `ModelRoute`, а новый раздел `Запуски` — v1 `Run`; это не переименование legacy-экранов.
- После переноса E2E-покрытия и проверки отсутствия нужных пользовательских данных legacy UI/API удаляются отдельным безопасным изменением.

## Границы сценария Dataset

Черновик владельца описывает четыре уровня сложности:

1. Готовые размеченные данные — базовый обязательный поток.
2. Исходные данные без эталонов — assisted labeling с пользовательской валидацией.
3. Нет данных — synthetic generation или подключение внешнего источника.
4. Произвольные форматы и media — mapping/import pipeline и Asset storage.

Текущий CSV/JSONL import закрывает только первый уровень. Поддержка «любого формата» не означает неограниченную магию импорта: нужен явный preview, предложенная mapping/schema, подтверждение пользователя и воспроизводимый transformation snapshot. Поиск данных во внешних источниках — отдельный post-MVP connector workflow.

Первый bounded mapping-инкремент покрывает text Dataset: пользователь после исходного preview явно сопоставляет поля файла с `external_id`, `input.text` и optional `reference`. Рядом показываются первые три исходные строки по найденным полям, чтобы проверить смысл данных, а не только названия колонок. Предложенные значения видимы и не применяются до подтверждения; подтверждённое определение сохраняется в schema версии. Произвольные nested paths, массивы/media и вычисляемые transformations остаются следующим уровнем import pipeline.

## UX-вопросы, не блокирующие следующий инкремент

- Нужна ли верхнеуровневая сущность «Проект» для группировки нескольких датасетов, экспериментов и запусков. До появления подтверждённого сценария новая доменная сущность не вводится.
- Должны ли получение candidate outputs и оценка быть двумя отдельными Run либо стадиями одного Run. Текущая модель поддерживает единый snapshot; UX может показывать стадии без преждевременного разделения хранения.
- Насколько свободным должен быть конструктор evaluator algorithms. Исполняемый пользовательский код требует plugin SDK и sandbox и не входит в MVP; declarative criteria и Judge покрываются раньше.

## Порядок миграции

1. Добавить summary matrix и item detail поверх существующего v1 Run API, чтобы завершить ценность уже работающего быстрого запуска.
2. Выделить из Workbench переиспользуемые компоненты и route-level экраны без изменения доменных контрактов.
3. Ввести новую навигацию и убрать legacy-пункты из header; оставить временные `/legacy/...` routes.
4. Перенести/расширить E2E на новый основной цикл.
5. После проверки данных и совместимости удалить legacy UI/API отдельным решением.
6. Затем развивать Dataset assets, assisted labeling, evaluator library и Judge workflow.

## Критерии приёмки перестройки

- Быстрый запуск доступен с Главной и приводит в конкретный v1 Run.
- Dataset, модели, эксперимент и результаты имеют собственные URL и восстанавливаются после refresh.
- Основная навигация не содержит legacy `Providers`, `Tasks`, `Test Runs`.
- Один объект не редактируется одновременно в нескольких несогласованных формах.
- История и snapshot существующих v1 Run остаются доступны.
- E2E проходит новый сквозной путь и больше не считает legacy navigation продуктовым требованием.

Завершены пункты 1 и часть пункта 3: Run получил summary/item detail, создан самостоятельный раздел `/runs`, legacy-пункты убраны из header и перенесены под `/legacy/...`. Следующая граница — самостоятельные «Датасеты» и «Модели», после чего Главная перестанет содержать их подробные формы.

Самостоятельные `/datasets` и `/models` реализованы и добавлены в основную навигацию. Формы импорта Dataset и управления ModelRoute удалены с Главной. Следующая граница — `/experiments`: туда переносятся Prompt/Pipeline/EvaluationSuite и подробный estimate/start, после чего Главная остаётся быстрым входом.




## Experiments navigation and recoverable Dataset publication — 2026-09-18

- /experiments содержит подробные формы Prompt/Pipeline/EvaluationSuite, estimate/start; Главная оставляет быстрый запуск и результаты. Общий Workbench временно используется в двух явных режимах; удаление старого неиспользуемого setup-кода остаётся следующим техническим шагом.
- Выбранная конфигурация сохраняется в sessionStorage текущей вкладки. /evaluation перенаправляет в /experiments.
- Dataset save запоминает draft, сверяет все существующие строки с preview и при полном совпадении повторяет только публикацию. «Продолжить» загружает все строки черновика постранично. При несовпадении данные не перезаписываются.
- Playwright 1/1 прошёл с искусственным обрывом publish v2, повторной публикацией, переходом Главная → Эксперименты, подробным запуском и экспортом. Backend-контракт в этом инкременте не изменён.
- Следующая пользовательская проверка: расположение подробных настроек в Экспериментах. Следующий технический шаг: вынести переиспользуемые компоненты и удалить мёртвый setup-код Workbench.
