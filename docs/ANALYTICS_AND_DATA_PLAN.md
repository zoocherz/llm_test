# План аналитики и подготовки данных

## Принцип

К реализации переходим после утверждения контрактов, пользовательских потоков и первого набора acceptance criteria. Реальные API-ключи и большой датасет для этого не нужны.

## Этапы до кода

1. Зафиксировать универсальную доменную модель: Dataset, Pipeline, EvaluationSuite, Run и Evaluator.
2. Описать API-контракты и wireframes основных экранов.
3. Сформировать каталог базовых evaluator types и правила создания custom evaluators.
4. Определить adapter contract и capability matrix провайдеров.
5. Подготовить минимальные репрезентативные наборы данных.
6. Утвердить критерии готовности первого вертикального среза.
7. Только затем реализовать foundation и тесты.

## Сбор минимальных данных

Для первичной разработки достаточно небольших наборов, не являющихся окончательной разметкой.

### Food vision smoke dataset

- 5–10 реальных или открытых фотографий.
- Один или несколько локальных файлов на запись.
- Короткая инструкция: например, определить блюдо и видимые ингредиенты.
- Необязательный reference; если его нет, используется Judge.
- Metadata: источник, язык, категория, заметки о сложности.

### Call annotation smoke dataset

- 5–10 обезличенных транскриптов либо открытых диалогов.
- Одна инструкция аннотации.
- Несколько reference-полей, если они доступны: summary, topic, intent, action items.
- Metadata: длительность, язык, тип разговора.

Эти наборы проверяют универсальный import, prompt variables, text/media передачу, result storage и evaluator APIs. Они не предназначены для статистически значимого выбора модели.

## План построения рабочих датасетов

1. Сначала определить, какое решение должен подтверждать датасет: выбор модели, промпта, pipeline или Judge.
2. Составить таксономию ситуаций и ошибок.
3. Отобрать репрезентативные примеры, включая сложные и негативные случаи.
4. Описать инструкцию разметки и схему reference.
5. Разметить двойную выборку и устранить расхождения.
6. Версионировать набор, фиксировать происхождение и ограничения.
7. Выделить immutable holdout dataset для финального сравнения.

## Вопросы для проработки

- Какие типы входов критичны в первые полгода: text, image, audio, document, video?
- Нужны ли tool calls, RAG, structured output и streaming уже в архитектуре v1?
- Какой предел локального датасета: число строк, размер asset и параллельность?
- Какие агрегаты нужны для выбора победителя: среднее, minimum threshold, percentile, weighted score?
- Какими правами и политиками хранения должны управляться чувствительные звонки и изображения?
- Какие custom metric rules обязательны до sandboxed scripts: формулы, regex, JSONPath, Python?
- Как задавать pipeline: JSON/YAML import, визуальный редактор или оба?

## Решение о первом вертикальном срезе

Food vision остаётся первой демонстрацией, но не первой доменной моделью. Он должен проходить через те же generic DatasetItem, Asset, Pipeline node, ModelRoute и Evaluator, которые затем использует аннотация звонков.
