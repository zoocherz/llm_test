# Следующий инкремент: выполнение инструкций и настоящая оценка

Статус: владелец подтвердил раздельный поток генерации и оценки; первый text-инкремент реализован. Финальные проверки и реальный smoke описываются в PROJECT_STATE. 2026-09-18.

## Подтверждённые ограничения текущего прототипа

Исторический аудит ДО этого инкремента. Ниже зафиксированы обнаруженные проблемы; применение промпта и настоящий отдельный Judge теперь реализованы. Исполнение произвольного DAG остаётся вне этого инкремента: неподдерживаемая схема отклоняется явно.

- EvaluationRunner передаёт модели input.text (или fallback), но не применяет сохранённый PromptVersion.template. Выбор промпта пока сохраняется в snapshot, а не управляет содержанием запроса.
- Числовой score сейчас равен 1 при непустом входном тексте. Результат записывается с evaluator_id=judge, хотя внешний Judge не вызывается. Это техническая заглушка, не измерение качества; интерфейс теперь предупреждает об этом.
- judge_enabled влияет на estimate, но не включает отдельного Judge в runner. Оценка числа вызовов не является подтверждением выполненных Judge-вызовов.
- Pipeline хранит graph definition, но executor выполняет один generate-вызов. Произвольный DAG не реализован.

Рефакторинг интерфейса не меняет старые RunSnapshot или сохранённые результаты. Указанные ограничения нельзя считать закрытыми прохождением offline smoke.

## Предлагаемый следующий объём

Этот объём реализован первым ограниченным инкрементом; автоматическая оценка одновременно с генерацией не добавлялась.

1. Сначала сделать выполнение одного PromptVersion честным: подстановка явных переменных из input, ошибка отсутствующей переменной до внешнего вызова, immutable snapshot и тест точного provider payload. Без произвольного выполнения кода в шаблоне.
2. Разделить получение candidate output и его оценку в пользовательском потоке, как предложено в docs/scenarios.md: пользователь сначала получает ответы, затем выбирает критерии и Judge.
3. Оценивать уже сохранённые ответы без повторного вызова candidate-моделей. Каждая оценка фиксирует source Run/items, версию правил, Judge ModelRoute и PromptVersion. Повторная оценка не перезаписывает прошлую.
4. Сначала один Judge route и один структурированный ответ с несколькими критериями. Ответ проверяется по schema и шкале; ошибка Judge не превращается в score=0. Показываются rationale, latency, usage и отдельный статус оценки.
5. Сначала offline/contract tests; реальные бесплатные модели — только явный пользовательский запуск, с предварительным показом количества Judge-вызовов. Доступность бесплатной модели и лимиты не гарантируются приложением.

## Подтверждённое решение владельца

Владелец подтвердил: «Да, генерация и оценка отдельно». Первый рабочий поток: получить ответы → отдельно оценить сохранённые ответы. Candidate-модели при оценке повторно не вызываются. Повторная оценка создаёт новую запись и не перезаписывает предыдущую.

После выбора аналитика/архитектура должны определить связь новой оценки с RunSnapshot и EvaluationSuite, API, воспроизводимость и UX до реализации. Не вводить скрытый второй вызов модели и не удалять legacy-данные в рамках этого инкремента.

## Контракт первого инкремента

- Генерация создаёт Run с kind=generation и не записывает EvaluationResult. Оценка объёма считает только candidate calls. Старые snapshots и технические scores остаются неизменными и помечаются в UI как legacy.
- Prompt поддерживает только {{field}} для верхнеуровневых полей input. Строка подставляется буквально, другие JSON-значения сериализуются; нет eval, выражений, доступа к файлам или окружению. Отсутствующие поля и неподдерживаемый синтаксис отклоняются до запуска. Executor читает шаблон из snapshot.
- Отдельная оценка — новый универсальный Run kind=evaluation, с source_run_id, Judge route/prompt, criteria/weights/threshold и копиями оцениваемых input/reference/output в snapshot. Новая таблица Experiment не нужна. Каждый item сохраняет связь с исходным item. Источник terminal; включаются только completed items с текстовым ответом.
- POST /runs/{source_id}/evaluations принимает judge_route_id, judge_prompt_id, suite_version_id. GET того же пути возвращает историю оценок. Прогресс, details и export используют существующие Run API. Повторный POST создаёт новую оценку; source Run не меняется.
- Судье передаются input, reference и output как данные; инструкция задаётся отдельным PromptVersion с {{input}}, {{reference}}, {{output}}. Сервер добавляет rubric и строгий JSON-контракт: scores по каждому ключу в диапазоне 0..1 и rationale. Weighted score вычисляет сервер. Невалидный JSON/шкала/набор ключей — failed item без numeric_score. Offline Judge — явно обозначенный тестовый режим, не оценка качества.
- UI: в завершённом generation Run действие «Оценить ответы», выбор Judge и правил, поле инструкции; до подтверждения показывается число вызовов. Новая оценка открывается в /runs/:id, содержит ссылку на источник. Предыдущие оценки доступны в истории источника. Никаких автоматических внешних вызовов при открытии формы.
- Acceptance: exact prompt provider payload; generation без score; отдельный Judge без candidate calls; повторные оценки не меняют источник; errors не превращаются в 0; snapshot сохраняет удалённые настройки; экспорт/навигация/регрессии offline. Реальный smoke выполняет владелец.
